# Pickle [仮] — 管理画面（運営バックオフィス）要件（統合版）

> 作成日: 2026-05-28 / 体制: 3名の設計チーム（Trust&Safety / 運用・施設 / 管理基盤・分析・権限）が並行設計し統合。
> 前提: 全国対応の個人単発募集サービス。サービス＝最小構造化された募集投稿＋自由本文＋1対1 DM＋外部予約導線＋プロフィール＋認証（会員/ゲスト）。**UGCあり**。予約在庫・空き枠・決済はシステム対象外。技術＝Expo(RN)＋Next.js＋Supabase、モノレポ(pnpm+Turborepo)。

---

## 0. 最初に握るべき3つの重要フラグ（機能洗い出しより優先）

1. **⚖️ 出会い系サイト規制法（インターネット異性紹介事業）の該当性**
   公開プロフィール＋1対1 DM＋面識のない人が会う、という構造は同法に**該当し得る**。該当する場合は **公安委員会への届出・18歳未満利用禁止・年齢確認が法的義務**。「練習相手」名目でも運用実態で判断されるため、**設計初期に弁護士確認が必須**。年齢確認の要否＝プロダクト根幹に影響。
2. **🍎 Apple App Store ガイドライン1.2（UGC）**
   通報機能・**24時間以内の対応（削除＋投稿者排除）**・ブロック・公開連絡先・規約同意が必須。「機能がある」だけでなく「実際に24時間以内に対応する運用体制」まで求められる。
3. **📄 情報流通プラットフォーム対処法（旧プロバイダ責任制限法・2025/4施行）**
   権利侵害投稿の削除申請受付・**発信者情報開示請求への対応**（IP/タイムスタンプ等のログ保全）。重い透明化義務は大規模指定事業者向けだが、削除申請受付と開示対応の一般義務は規模を問わず負う。

→ 管理画面の設計は上記を満たす形（通報キュー＋SLA、ログ保全、年齢確認）を**MVPから**織り込む。

## 1. 管理者ロール（RBAC）と運用前提

- ロール: **super_admin / moderator / facility_staff / viewer**。
- 少人数でも「viewer（閲覧のみ）」を用意すると施設スタッフ・委託先に安全に開放可能。
- 管理者は Supabase Auth を流用しつつ `admin_users(user_id, role, status)` で**別管理**。ロールは改変不可の `app_metadata` に保持（`user_metadata`では判定しない）。
- **管理者ログインは2FA(TOTP)必須**（BAN/削除など破壊的操作を持つため）。
- **設計原則**: 破壊的操作は全て **論理削除＋監査ログ**。
- ※予約在庫・空き枠の管理は対象外。投稿の地域/場所/日時は管理対象に含める。提携施設リンクは将来 `facility_links` として軽量管理する余地あり。

### D. Trust & Safety / モデレーション（本サービスの心臓部）
| 機能 | 優先 | 目的 |
|---|---|---|
| 通報導線（投稿/DM/ユーザー/プロフィール、理由カテゴリ付き）※アプリ側 | MVP | Apple 1.2必須 |

| 通報詳細（対象全文・通報者/被通報者・過去履歴を1画面） | MVP | 即断トリアージ |
| ユーザー制裁（警告/一時停止/永久BAN・履歴タイムライン） | MVP | Apple 1.2「乱用者排除」 |
| メール/端末単位ブロック（再登録防止）・シャドウバン | P2 | 作り直し荒らし対策 |
| 異議申立・解除フロー | P2 | 誤BAN救済・透明性 |

**DMの扱い（方針）**: **原則運営は読まない。通報されたスレッドの該当抜粋のみ閲覧可**にし、**DM閲覧操作自体を監査ログに残す**。プライバシーポリシーに「通報時・法令時のみ確認」と明記。常時監視は信頼毀損＋漏えい時被害が甚大。

**リアル接触の安全（マッチング特有）**: 接触前の安全ガイド表示、緊急/相談導線（＝公開連絡先も兼ねる）、ドタキャン/ハラスメント対応フロー（評価機能は報復・晒しに転用されやすく導入は慎重に）。

## 4. 管理画面の実装方式（比較・推奨）

| 方式 | 初期工数 | ランニング | カスタムUI | Supabase連携 | ロックイン |
|---|---|---|---|---|---|
| (a) Next.js 自作 `apps/admin` | 大 | ほぼ無料 | ◎ | ◎ | なし |
| (b) Supabase Studio 直 | ゼロ | 無料 | ✕ | ◎ | なし |
| (c) Retool/Appsmith 等ローコード | 小 | **席課金** | ○ | ○ | あり（ツール側に滞留） |
| (d) Refine（OSS管理画面FW） | 中 | 無料(自前ホスト) | ◎ | ◎(Supabaseプロバイダ標準) | なし |

**推奨：(d) Refine ベースで `apps/admin` を構築（実質 a+d ハイブリッド）**
- モノレポに `apps/admin` として追加、型・認証・UIを共有。
- 通報キュー/一覧/詳細など**CRUDのボイラープレートを大幅削減**。
- 席課金なし・コード所有（Retoolはコード非所有＋人数課金で継続運用に不向き）。
- **超初期はSupabase Studioで代用**し、`apps/admin`は通報キュー＋監査ログ＋お知らせから着手。

**管理操作の共通経路**: 管理画面 → Edge Function(service_role) で ①管理ロール検証 ②本処理 ③監査ログ追記 を1トランザクション。一般ユーザー向けRLSに管理分岐を混ぜない。

## 6. MVPで最低限作る管理機能（まとめ）
1. 会員：一覧/ステータス/レベル補正/退会・削除
2. 投稿：一覧/非表示/クローズ/ピン留め＋**シード・運営投稿・テンプレ**
3. お知らせ＋規約バージョン管理（同意連動）
4. **T&S最小**：通報キュー(SLA 24h)→非表示/凍結、ユーザー制裁、通報DM限定閲覧
5. 監査ログ（追記専用＋閲覧UI）
6. 問い合わせ受付＋ステータス
7. メンテ/機能フラグ、最小KPIカード、データ削除＋バックアップ手順
8. 管理者RBAC＋2FA
※コート/施設は**予約在庫管理なし**。MVPでは外部予約リンク設定に留める。

## 7. ロードマップ
- **MVP**: Refineベース`apps/admin` → 通報キュー＋制裁＋論理削除 → 監査ログ → 会員/投稿/お知らせ → 問い合わせ → メンテ/フラグ → 最小KPI → 削除対応＋バックアップ → RBAC＋2FA。
- **Phase2**: マッチング系KPI＋日次集計、Expo Push一斉配信、NGワード自動フラグ、CSVエクスポート、PostHog/GA4、異議申立フロー、ヒートマップ。
- **将来**: セグメント/予約配信＋効果測定、メールサポート連携、イベント/大会管理（まず外部委譲を検討）。

## 8. 主要リスク
- 24時間対応の実体制（夜間/休日の穴）→ 重大通報のプッシュ/メール通知＋モバイルでも処理できる管理画面。
- DM閲覧の内部統制（通報時のみ＋閲覧ログ）。
- 出会い系規制法の該当性（年齢確認・届出の要否＝根幹）。
- ログ保全と削除のジレンマ（論理削除＋保持期間ポリシー）。
- 誤BAN/恣意運用 → 制裁基準のガイドライン化＋異議申立。
- RLS設定不備（全テーブル有効化・service_role非露出・参照列のインデックス）をリリース前に監査。
